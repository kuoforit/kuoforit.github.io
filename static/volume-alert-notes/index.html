Volume Alert Field Notes

A small program on a Raspberry Pi 5 at home. Every minute it pulls the latest 5-minute candles for every Binance USDT-margined perpetual, decides which coins just saw abnormal, sudden volume, and pushes them to a Discord channel through a webhook.

These notes document how it works end to end: where the data comes from, how the decision is made, and how the message reaches Discord.

A spike has to be unusual against the last three days and sudden against the last four hours.The one-line version of the rule

Data flow

01

Blue: inside the Pi5. Orange: requests to Binance. Green: delivery to Discord.

Each outside party has exactly one job. The Pi5 schedules, computes and keeps state. Binance is only read from. Discord is only written to. Data moves one way; nothing comes back from Discord.

One minute, step by step

02 · ~15–18 s per run
hh:mm:05
The systemd timer starts binance-volume-alert.service, a one-shot job. If the previous run is still going, a second one is not started on top of it.
+0.3 s
Load thresholds and the webhook URL from .env. Ask Binance for the contract list and keep the ones that are USDT-quoted, perpetual and trading, currently about 525.
+0.5 s
Over 32 parallel connections, fetch the latest four 5m candles for every coin: three closed plus the one still forming. Coins whose cache is missing or stale get the full 868-candle history instead, at most 300 per run.
+12 s
Append newly closed candles to the in-memory cache, keeping the last 867 USDT volumes per coin.
+13 s
For each coin, score the just-closed and the still-forming candle: compute the 72h and 4h medians, apply rules ①–⑤, then check state.json to decide whether this is a new alert.
+14 s
POST any alerts to the Discord webhook: one card per coin, or a single list if 15 or more coins fire at once. Write one summary line to the log and exit.

Pi5: files & schedule

03 · Raspberry Pi OS

The script uses only the Python standard library, so nothing needs to be installed. Scheduling is plain systemd, the same pattern as the other projects on this Pi.

PathWhat it holds
~/binance-volume-alert/volume_alert.pyThe program. Runs top to bottom and exits.
~/binance-volume-alert/.envAll thresholds plus the Discord webhook URL. Mode 600: readable only by the user that runs the job.
~/binance-volume-alert/state.jsonWhich candles have already been sent, and each coin's current "wave" (the volume the next alert has to double).
/dev/shm/binance-volume-alert-5m.jsonThe last 867 five-minute USDT volumes per coin. Lives in RAM so the SD card isn't rewritten every minute; cleared on reboot and refilled in two runs.
…/systemd/system/binance-volume-alert.serviceType=oneshot, runs as a normal user, EnvironmentFile= points at .env.
…/systemd/system/binance-volume-alert.timerOnCalendar=*-*-* *:*:05, AccuracySec=1s, enabled at boot.

Deploying

The source lives on the laptop in a local git repo. ./deploy.sh does three things:

  1. Stops the timer on the Pi, so no run straddles the code swap.
  2. Copies the script, .env.example and both systemd units over with scp.
  3. Runs daemon-reload and re-enables the timer.

It never overwrites the Pi's .env, so the webhook URL never touches the laptop or git.

Binance API: what is fetched

04 · fapi.binance.com

Only public market data. No API key, no account, nothing that could place an order.

EndpointPurposeCalls / runWeight
/fapi/v1/exchangeInfoContract list. New listings join automatically, delisted ones drop out.11
/fapi/v1/klines limit=4Latest four 5m candles per coin (normal runs).≈5251 each
/fapi/v1/klines limit=868Full history (first start, reboot, config change).≤3005 each

Fields used: open time, open price, close price (the current price for a forming candle), quote volume in USDT, and trade count. Volume is always measured in dollars so that coins are comparable.

Budget: Binance allows 2,400 weight per minute per IP. A normal run uses about 526 (≈22%); the two backfill runs after a restart use about 1,500.

Shared IP. The Pi shares its public IP with every other device on the home network, and they all draw on the same 2,400. Heavy backtests from the laptop once ate the whole budget and stretched Pi runs from 15 seconds to two minutes. The script now gives up a run immediately on 429 (rate-limited) or 418 (banned) instead of retrying, and tries again the next minute.

Baselines

05 · all volumes in USDT

Two candles are scored per coin per run: the one that just closed, and the one still forming. The forming candle uses the volume traded so far. Volume only grows, so if it already passes, the closed candle will pass too. That's what lets alerts fire before the candle ends.

BaselineDefinitionQuestion it answers
Long-termMedian of the previous 864 candles (72 hours)Is this unusual for this coin over the last three days?
Short-termMedian of the previous 48 candles (4 hours)Is it sudden, or has volume been this high for hours?

Medians rather than means: one big spike in the window would drag a mean up and hide the next spike. Neither baseline includes the candle being scored.

Each baseline catches the other's blind spot. A quiet night drags the 4h median down, so ordinary morning volume would look "sudden"; the 72h baseline says it's just normal. A coin that has been running hot all day keeps beating its 72h median; the 4h baseline says it's the same as an hour ago. Requiring both leaves the genuinely abrupt moves.

Trigger rules

06 · ① AND (② OR ③ OR ④ OR ⑥), OR ⑤
Single-candle spike: ① must hold, plus at least one of ②③④⑥
①Volume ≥ 5× the 4h median — sudden, not already elevated
②≥ 10× the 72h median and ≥ $2M — a normal spike
③≥ 100× the 72h median and ≥ $500K — an extreme spike on a small coin
④≥ 30× the 72h median and ≥ $1M — the gap between ② and ③
⑥≥ 10× the 72h median, ≥ 15× the 4h median and ≥ $1M — a quiet coin waking up, below ②'s $2M and ④'s 30×
or
Sustained spike
⑤Three candles in a row, each ≥ 20× the 72h median and ≥ 5× the 4h median; together ≥ $500K; price move across the three ≥ 2%. The third candle may still be forming.

② through ④ exist because one dollar floor can't fit every coin. A large coin needs real size to matter; a coin that normally trades $4K per five minutes and suddenly does $550K is worth hearing about even though it never reaches $2M.

⑥ fills the gap that ② and ④ leave open: 10–30× normal with $1–2M of volume. It requires 15× the 4h median, three times ①'s bar, so it only fires on coins that were quiet right before. Large coins drifting just under $2M stay out.

⑤ covers moves that never produce a single big candle: several consecutive candles at 20–50× normal while price grinds higher. One fat candle on a small coin is often a single large order; three in a row with price following is more likely real interest.

Repeat control

07 · no time-based cooldown
  • One alert per candle, at most.
  • The first triggering candle starts a wave and always alerts.
  • Inside a wave, a later candle alerts again only if its volume is at least 2× the last alerted candle's. Those cards are titled ⏫ ESCALATING. If the last alert fired mid-candle, the comparison switches to that candle's final volume once it closes, so a half-finished candle doesn't make the bar too easy to clear.
  • Three candles in a row without a trigger (15 minutes) end the wave. The next trigger starts a new one.

An earlier version used a fixed 60-minute cooldown. It re-sent coins that stayed hot all day once an hour, and it could hide a second, larger leg that started 20 minutes after the first. "Only if it doubles" keeps accelerating moves visible without repeating plateaus.

Discord webhook

08 · one-way · free · no bot

A webhook is Discord's built-in way for an outside program to post into one channel. It can only send, never read, so there is no bot to create, no permissions to configure, and no connection to keep open.

Setup (once, in Discord)

  1. Create a text channel on your own server, e.g. #binance-alert.
  2. Channel settings → Integrations → Webhooks → New Webhook. Any name works.
  3. Copy Webhook URL. It looks like https://discord.com/api/webhooks/<id>/<token>.
  4. Put it in the Pi's .env as DISCORD_WEBHOOK_URL=….
The URL is the password. Anyone holding it can post to the channel. It exists only in the Pi's .env (mode 600), not on the laptop, not in git, not on this page. If it leaks, delete that webhook in Discord, create a new one, and swap the value; it takes effect on the next minute.

Sending

The script sends one HTTPS POST per message with Python's built-in urllib. The body is JSON:

POST https://discord.com/api/webhooks/<id>/<token>
Content-Type: application/json
User-Agent: binance-volume-alert/1.0

{
  "username": "Volume Alert",
  "embeds": [{
    "title": "🟢 ENSOUSDT — volume spike 135.3x",
    "url":   "https://www.binance.com/en/futures/ENSOUSDT",
    "color": 3063173,
    "fields": [
      {"name": "5m volume",       "value": "$556.63K",               "inline": true},
      {"name": "72h median (5m)", "value": "$4.11K",                 "inline": true},
      {"name": "Ratio",           "value": "135.3x 72h · 131.4x 4h", "inline": true},
      {"name": "Price",           "value": "0.9263 → 0.9736",        "inline": true},
      {"name": "Change",          "value": "+5.11%",                 "inline": true},
      {"name": "Timing",          "value": "at candle close",        "inline": true}
    ],
    "footer": {"text": "Binance USDT-M Futures · 5m candle · 3,412 trades"}
  }]
}

The structure of a real alert, ENSO at 12:15 on 2026-10-09. The volume and price values are from that candle; the trade count is illustrative. Discord answers 204 No Content on success, and the card appears in the channel and on the phone according to the channel's notification setting.

SituationWhat gets posted
One coin firesOne embed per coin; up to 10 combined into one message.
Rule ⑤Title "sustained volume (3 candles)", plus a line with the run length, total volume and price move.
≥ 15 coins at onceTreated as a market-wide move: one compact list, a line per coin sorted by ratio, BTC's ratio in the title, split every 60 lines.

Discord's limits and how they're handled

  • At most 10 embeds per message; consecutive messages are spaced one second apart.
  • Roughly 30 messages per minute per channel. On 429 Discord returns retry_after; the script waits that long and retries, up to three times.
  • An empty webhook URL means dry run: everything is logged, nothing is sent.
  • Webhooks are free; no Nitro needed.

Failures & logs

09 · journalctl
SituationBehaviour
One coin's request failsRetried twice, then skipped until next minute.
Binance 429 / 418No retry; the run is abandoned.
Over half the coins failThe run exits as failed and shows up in the log.
New candle not yet createdQuiet coins may have no trade in the first seconds of a candle; the just-closed candle is still scored.
Under 864 candles of historyNew listings are skipped and counted as short_history.
Pi rebootThe RAM cache is gone; the first two runs refill it.
 
$ journalctl -u binance-volume-alert -n 50
candle 15:45 scanned=525/525 backfill=0 short_history=0 errors=0 spikes=1 alerts=0 took=17.9s

scanned is coins with fresh data, backfill is coins refilled this run, spikes is candles that met a rule, alerts is messages actually sent, and took is wall time. When something is sent, a line per coin follows with its ratios, volume, timing and any ESCALATING / SUSTAINED flag.

Changing a lookback length invalidates the cache automatically: every coin's history is tagged with the length it was fetched for, and a mismatch triggers a refill.

Changelog & lessons

shipFirst version: 15m candles, checked every 15 minutes after the close, ≥5× the 72h average.

It worked, but alerts arrived up to 16 minutes after a move began, and one big past spike in the average hid the next.

2026-10-09
shipSwitched to 5m candles checked every minute, median baselines, and a compact list for market-wide moves.

A 1-minute replay later showed per-minute checks alert only ~1.4 minutes earlier on average than checking at each close. Useful, not dramatic.

2026-10-09
lessonLaptop backtests and the Pi share one public IP and one Binance budget.

Runs slowed to two minutes until the backtest stopped. Backtests now fetch once to disk and throttle themselves; the alert job no longer retries on 429.

2026-10-09
shipRule F: the 4h short-term baseline, the ③ extreme tier, and "re-alert only when volume doubles" instead of a 60-minute cooldown.

A coin that had run 40–160× its 72h median for seven straight hours stopped re-alerting every hour.

2026-10-09
bugFor almost three hours, 300 of 525 coins weren't monitored at all.

The code was deployed before the lookback setting changed, so the first batch got 288 candles of history instead of 864, and coins with short history were skipped without a word. Fixed by tagging the cache with its lookback and logging short_history. The log had said scanned=525/525 errors=0 the whole time, so a healthy-looking summary line isn't proof.

2026-10-10
shipAdded ④ (30× and $1M) and ⑤ (sustained, three candles).

Replayed against four moves that had been caught late, first alerts moved from +10–19% into the move to +4–6%, and one that was missed entirely is now caught. Hit rate on rule ⑤ is still unverified.

2026-10-14
shipAdded ⑥ (10× 72h, 15× 4h and $1M) after PYTH was missed.

PYTH's 11:00 candle did $1.40M at 13.7× the 72h median and 22.3× the 4h median, with price up 3.5%. It failed ② on dollars and ④ on the multiple, so no rule covered it. A 7-day backtest compared two fixes: lowering ②'s floor to $1M added 44 alerts a day, while ⑥ added 14 and still caught PYTH. Alerts added by either fix moved slightly less afterwards than the existing ones (median best move within 60 minutes 0.8% vs 1.0%), so this is about missing fewer coins, not sharper signals.
